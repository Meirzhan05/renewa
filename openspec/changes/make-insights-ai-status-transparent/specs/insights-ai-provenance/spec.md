## ADDED Requirements

### Requirement: Truthful Insight summary provenance
The system SHALL provide structured provenance for every non-null Insight report, including whether the summary was AI-generated or deterministic, its server-generated timestamp, whether this response reused a cache entry, and privacy-safe aggregate evidence counts. The client MUST present source wording that matches the provenance and MUST NOT present a deterministic summary as AI-generated.

#### Scenario: Fresh AI-generated report
- **WHEN** a request produces and validates a model-generated Insight report
- **THEN** the response SHALL identify the source as AI-generated and the client SHALL present an AI-generated source label with its generation time

#### Scenario: Cached AI-generated report
- **WHEN** a request returns a valid matching cached report generated by AI
- **THEN** the response SHALL identify the report as cached AI output and the client SHALL state that the displayed AI insight is cached

#### Scenario: Deterministic fallback report
- **WHEN** a model request or model-output validation fails and the system creates a deterministic report
- **THEN** the response SHALL identify the source as deterministic and the client SHALL label the card as a basic subscription summary rather than AI-generated

### Requirement: Privacy-safe evidence context
The system SHALL accompany a non-null Insight report with aggregate evidence counts sufficient to describe its scope. The client SHALL show only meaningful non-zero counts and SHALL NOT display raw email content, message subjects, OAuth credentials, report identifiers, provider errors, secret values, or model prompt text.

#### Scenario: Report has qualifying evidence
- **WHEN** a report is based on active subscriptions and/or qualifying billing events
- **THEN** the client SHALL state the relevant aggregate evidence counts beneath the summary

#### Scenario: Evidence count is zero
- **WHEN** an evidence category has no qualifying items
- **THEN** the client SHALL omit that category from the provenance line

### Requirement: Scoped degraded AI availability
The system SHALL preserve deterministic Insights content when AI generation is unavailable. The client SHALL render the degraded state within the Insight summary area with stable, non-technical language and a retry action, rather than replacing the entire dashboard or showing provider-specific error detail.

#### Scenario: AI fallback accompanies deterministic dashboard data
- **WHEN** AI generation falls back while subscriptions, trends, categories, or renewals are otherwise available
- **THEN** the client SHALL retain those deterministic sections and present the basic summary with an AI-unavailable explanation and retry action

#### Scenario: Full Insights request fails
- **WHEN** the Insights service request fails and no report is available
- **THEN** the client SHALL present a scoped retryable Insights state without exposing underlying provider or validation errors

#### Scenario: Account has no active subscriptions
- **WHEN** an account has no active subscriptions
- **THEN** the system SHALL not invoke AI generation and the client SHALL present the normal activation state without describing AI as unavailable

### Requirement: Non-disruptive refresh and freshness
The client SHALL retain a visible prior Insight report during a user-initiated refresh and present updating status without replacing the card with a loading skeleton. A forced refresh MUST bypass a matching cached report lookup and request a new analysis.

#### Scenario: User refreshes a visible report
- **WHEN** the user initiates an Insights refresh while a report is visible
- **THEN** the existing report SHALL remain visible with a non-blocking updating indicator until a replacement result is received

#### Scenario: User retries a degraded summary
- **WHEN** the user activates retry from a deterministic summary caused by unavailable AI
- **THEN** the client SHALL request a forced refresh and the server SHALL not return a matching cache entry solely because its fingerprint matches

### Requirement: Privacy-minimized AI outcome diagnostics
The server SHALL emit categorized diagnostics for cache reuse, successful AI generation, fallback, validation failure, and request failure. Diagnostics MUST NOT include secret values, authorization data, raw email content, model prompts, merchant names, full model output, or customer-facing error text.

#### Scenario: Model request fails
- **WHEN** the model request fails
- **THEN** the server SHALL record a categorized internal failure outcome and SHALL return only stable client-safe provenance or fallback information

#### Scenario: Cached report is reused
- **WHEN** a valid cache entry is returned
- **THEN** the server SHALL record a cache-reuse outcome without re-sending its fact payload to the model
